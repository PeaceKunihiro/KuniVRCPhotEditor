# v0.4.2 OCR・モデル候補記録 改修案

実装日: 2026-10-10。v0.4.1を基準とし、連写の最初のみ候補を記録する変更をユーザー承認済み。試験状況はUPDATELOG参照。

## 基本動作

1. 記録開始時に対象VRChatウィンドウの取得を開始する。単一起動で一意に選べる場合は自動選択し、複数ウィンドウはOCRタブで対象を選ぶ。画面全体の無差別取得や別アプリへの自動切替をしない。
2. 映像ファイルを生成して分割せず、キャプチャーフレームを設定FPSで間引いてメモリのリングバッファへ直接入れる。読み取りFPS初期5、期間初期10秒（約50枚）。取得時刻・単調時刻・サイズ・セッション・インスタンスを保持し、古いフレームを順次解放する。キャプチャー画像をディスクへ自動保存しない。
3. 初期モード「撮影時」は、新規写真の追加を入口としてバッファへOCRを実行する。撮影ログ・画像日時による時刻照合と書込み安定確認は既存処理を維持する。OCR開始は非同期に行い、保存の安定待ちの間に処理を進める。初期モードは負荷の低い撮影時を提案する。
4. OCRフレーム時刻の参加者一覧と撮影時点の参加者一覧を使い、正式名と取得済みIDに照合する。完全一致を優先し、類似一致は最低類似度・次点との差・複数フレームの支持を正解付きデータで校正する。類似一致で短い名前・同名・競合が解消しない場合は自動採用しない。常に最も近い人物へ割り当てる方式を避ける。
5. 採用できた人物だけをModelCandidatesへ追加する。手動確定モデル（Subjects）や既存の候補は消さず、既存の自動処理済み写真へ重複保存しない。候補は画面の文字から得た推測であり、写真内人物の確定とは扱わない。

バッファ全体を認識しても、撮影後のフレームはその写真の候補に使わない。古い観測の混入を減らすため、候補採用はStage3既存仕様の撮影前3秒とする（バッファ保持10秒とは別）。この期間や類似度の閾値は実画像で検証する。

## 連写時の除外と保存確定

- 同一セッション・インスタンスの最初の写真は候補記録対象とし、直前撮影からバッファ期間以下（初期10秒）の後続はInstanceMembersのみ記録する。連写が続くと最後の撮影から期間を測り直す。最初の候補は後続の発生で削除しない。
- 撮影時刻とインスタンスが照合できた時点で順序を確保し、保存安定待ち・OCR処理の完了順で最初を決めない。復元記録にも判定根拠を残す。遅れて発見した古い写真は保守的に後続扱いとする。
- 連写判定のための10秒未来待機は不要。画像書込み安定・既存の5秒ログ猶予・OCR待ちは残る。写真検知時に有効フレームを参照保持してOCRを開始する。
- 一度のAB_バックアップ付き上書きで同室者と候補を確定する。AB_、監視開始前の既存写真、重複通知を連写枚数に数えない。停止後に未着手の写真を勝手に保存せず、開始済みの置換は安全に完了する。

## 候補なしと取得状態

- 読取文字なし／有効な一致なしでは人物を追記しない。既存候補を削除せず、架空の人物や空文字の候補を作らない。
- 人物配列への追加と状態記録を区別する。正常に認識・照合したが採用ゼロはno-match、未取得・エンジン未準備・期限超過はnot-observed。連写による意図的省略は新状態skipped-burstとして記録し、表示を「連写のため候補記録なし」とする案。新状態へ対応する表示も同時に実装する。
- 候補ごとの正式表示名・ID・OCR原文・取得時刻・観測回数・照合方法・スコアを保存する。エンジンがOCR信頼度を提供しない場合は値を捏造しない。既存手動モデルと別に保持する。

## キャプチャーと負荷

- Windows Graphics Capture＋Direct3D 11を第一候補とする。CreateFreeThreadedでUIとは別の取得処理を使い、GPUメーカー固有APIへ依存しない。Radeon／GeForce双方を対象とし、実機互換性は別途検証する。非対応・ウィンドウ閉鎖・最小化・取得停止・サイズ変更・GPUデバイス喪失を検出し、他の画面を代替取得しない。
- 取得フレームを直ちに解放し、指定FPSで採用するものだけをバッファ用資源へコピーする。GPU上で切出し／縮小を検討し、CPU読戻しとOCRは必要な画像に限定する。独立OCRワーカー、有限待ち行列、認識済み結果の再利用を使う。撮影時と常時の両モードで同じ時刻・セッション制約を適用する。
- 無圧縮フルHD・BGRAで5FPS×10秒は約396MiB、4Kでは約1.55GiBになる。枚数／秒数だけでは上限にならないため、バッファ資源・実行中画像を含むバイト上限を追加する。保持画像に256MiBの上限を設定し、設定量に合わせGPUで最大1920×1080へ縮小する。灰色と黄色文字マスクの2画像を保持する。実行中OCRの参照も画像予算に含み、容量不足時は新フレームを省略して状態表示する。縮小による認識品質・実保持秒数の実測は残課題。GPU資源や認識器内部作業メモリは画像予算とは別。
- 読み取りFPSはキャプチャーバッファの採用頻度で、OCR処理の実速度とは分ける。暫定設定範囲5〜15FPS、期間1〜30秒を提案する。常時OCRは最新未認識フレームを処理し、撮影ジョブは最大4件とする。写真処理は既存の60秒再試行期限を使い、待ち行列やメモリを無制限に増やさない。
- 今回の初期実装はWindows OCRを利用し、利用可能な日本語／英語モデル、またはユーザー言語モデルを使う。認識器・言語モデルの同梱や自動インストールは行わない。モデル未準備なら同室者のみ記録し未観測理由を表示する。正解付き実データでの精度校正とポータブル認識器は残課題。GPUキャプチャーを採用してもOCR自体がGPU処理になるとは限らない。

## UIと停止

- 記録開始／停止ボタンで監視・キャプチャー・OCRを連動する。OCRが利用できない場合も同室者記録は継続し、未取得理由を表示する。
- 記録中はサイドビューのプレビューをキャプチャー確認画面にする。画像選択はメタデータ表示を更新するが、確認画面は選択画像で置き換えない。停止すると選択画像のプレビューへ戻す。サイドビュー「なし」は取得を続けて表示だけ省略する。
- 最後の取得画面をライブと誤解しないよう停止／未取得・対象名・取得FPS等を併記する。確認画面はフレームごとのUI全面更新を避け、更新を採用FPS以下へ制限する。
- 「シンプル」「詳細」に続いて「OCR」タブを追加。「常に／撮影時」トグル、読み取りFPS（初期5）、バッファ期間（初期10秒）、読取った生のOCR結果を読取り専用・スクロール可能で表示する。原文と候補名を混同せず、取得／実行中／完了／省略／失敗も表示する。大量の原文は表示量を制限する。
- 常にモードは記録ON中に認識を逐次実行、撮影時モードは通常バッファ取得のみで追加時に認識する。同じフレームの重複認識を避ける。設定変更時はバッファを再構成し、古い設定の観測を混ぜない。設定はEXE配下へ保存、起動時の記録状態はOFFを維持する。

## 検証と一次資料

- 合成時計で1枚撮影、期間境界の2枚、連写継続、重複通知、通知遅延、停止中待機を試験し、最初の写真が候補対象で後続だけが省略されることとバックアップ一回を確認する。
- ログ切替・入退室・同名／類似名・短い名前・不一致・認識失敗を検証する。正解付き参考データがない現在、類似一致の実精度は未検証。実写真の原本は読取り専用を維持し、書込みは専用試験画像のみ。
- 両GPU系統、ウィンドウ移動／縮小／最小化／閉鎖、表示モード、負荷・実採用FPS・メモリ上限・UI応答を実機で確認する。Debug／Releaseの既存試験を継続する。
- [Microsoftの画面取得説明](https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/develop/media-authoring-processing/screen-capture.md)：フレームSurface・ContentSize・QPC基準時刻を取得し、UIでの重い処理を避ける。
- [CreateFreeThreaded](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded?view=winrt-26100)：内部ワーカースレッドでFrameArrivedを通知する。
