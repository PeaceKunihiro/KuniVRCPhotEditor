# JSON保存ファイルの統合候補

調査日: 2026-10-24。以下はv0.6.1時点の調査・提案。後続指示により[v0.6.2で実装](V0.6.2_IMPLEMENTATION.md)した。

| 現在のファイル | 役割 | 推奨 |
|---|---|---|
| settings.json | 閲覧・UI・キャッシュ等の設定 | 統合先 |
| ocr-settings.json | OCR設定 | settings.json内のocr節へ統合可能 |
| stage3-settings.json | ログ・写真監視と記録設定 | settings.json内のrecording節へ統合可能 |
| backups.json | 自動バックアップの管理記録・指紋 | 設定とは分離を維持 |
| stage3-journal.json | 自動記録の保留・再開情報 | 設定とは分離を維持 |
| IdDisplayNames.json | IDと表示名の独立対応表 | 独立管理・Import/Export仕様を維持 |

生成されるファイルは利用機能により異なる。基本の5種に加えて、対応表利用時はIdDisplayNames.jsonも対象となる。実データ本文は調査に不要なため読み取らず、保存経路・役割をソースで確認した。

## 判断

3種類の設定は1つへ統合可能。ただし現状はUI・OCR・監視で保存処理とロックが別々なので、単に同じファイル名へ変更すると古い状態で他節を消す危険がある。共通の保存窓口で節の更新を直列化し、一時ファイルからの置換と破損原本の保全を維持する必要がある。OCRロック等を保持したまま共通保存側から別機能へ再入しない設計にする。

バックアップ管理記録は画像置換前の保存成功が必須で、指紋に基づく自動整理にも使用する。ジャーナルは記録処理に合わせて更新され、再開時の保留情報を保持する。これらを通常設定と一体化すると書込み範囲と障害影響が増えるため、分離を推奨する。対応表はユーザーが独立管理・Import/Exportする既存仕様を維持する。

直下を整理する目的には、settings.jsonだけを直下に置き、残る管理記録・対応表をEXE配下のDataフォルダーへ格納する案が適する。ファイル総数の削減と配置の整理を分けて扱う。移行時は新ファイルの保存・再読込み確認後に切り替え、失敗時は旧ファイルを保全する。設定版・旧新共存時の優先順位と、旧版へ戻す場合の扱いも実装前に確定する。

将来の背景保持管理を追加する場合も、背景設定・保持情報の保存先をこの整理と合わせて決め、新たな直下JSONを安易に追加しない。背景の削除対象を証明する情報の耐久性は、単なる表示設定と区別して設計する。

## 実装時の確認候補

- 各旧設定の移行、初期値・Unicode・ID保存ON/OFFの維持。
- UI／OCR／記録設定の連続・同時更新による他節の欠落防止。
- 破損・容量不足・保存権限なし・途中失敗で原本と従前設定を保持。
- バックアップ管理保存失敗時に写真を置換しないこと、ジャーナルの再開判定と対応表Import/Exportの維持。
